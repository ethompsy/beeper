## What Went Well

### 1. Zero CRITICAL Code Review Issues

A major improvement over Epic 2: all 36 code review findings across 7 stories were MEDIUM or LOW severity. Epic 2 had 7 CRITICAL issues (1 per story). This suggests the development approach matured — foundational patterns established in earlier epics prevented the class of critical bugs (missing endpoints, serde inconsistencies, dead write paths) that plagued Epics 1-2.

### 2. Excellent Service Layering and Reuse

Epic 3 demonstrated strong architectural layering with progressive reuse:
- **Story 3-1** (TrustLevelService) established the foundation
- **Story 3-2** (ConfidenceGateService) built on trust levels
- **Story 3-3** reused 3-2's backend entirely — zero new backend code, pure UI layer
- **Story 3-5** (AdaptiveThresholdService) consumed both trust levels and feedback data
- **Story 3-6** (EscalationUrgencyService) integrated SLO data with trust-level dampening
- **Story 3-7** (NoiseReportService) aggregated feedback from 3-4 and false page data from Epic 2's NotificationAuditService

This progressive composition meant later stories were faster and less risky because they built on stable, tested foundations.

### 3. Zero New Dependencies

Not a single new package was added across all 7 stories. Everything was built using existing libraries (Qdrant client, HTMX, Jinja2 templates, httpx). This continues the "zero new dependencies unless justified" policy and represents the cleanest dependency profile of any epic in v0.2.0.

### 4. Consistent HTMX Integration Pattern

Every story followed the same UI integration pattern:
- HTMX lazy-loaded sections (`hx-get` + `hx-trigger="load"`)
- Inline update forms with `hx-post` + `hx-swap`
- Partial template re-rendering for progressive enhancement
- SSE events for real-time cross-viewer updates (3-4 feedback, 3-6 urgency)

This consistency reduced UI integration risk and made each story's UI work predictable.

## Challenges & Growth Areas

### 1. Boolean Bypass Validation — Recurring Bug Pattern (5 of 7 Reviews)

The most significant recurring issue: boolean values (`True`/`False`) bypassing numeric validation checks. This was caught in code review for Stories 3-1, 3-2, 3-3, 3-5, and 3-7.

**Pattern:** Python's `isinstance(True, int)` returns `True`, so boolean values pass `int`/`float` validation. Without explicit `isinstance(value, bool)` guards before numeric checks, `True` maps to `1` and `False` to `0`.

**Impact:** In 3-1, `True` was accepted as a valid trust level. In 3-2, boolean confidence scores passed validation. In 3-3, `isinstance(threshold_str, bool)` checked a string variable (always `False` — dead code). In 3-5, boolean thresholds bypassed float conversion. In 3-7, `_iso_to_epoch` had similar issues.

**Root Cause:** No project-wide validation utility. Each story independently implemented input validation, and each independently missed the boolean edge case.

**Lesson:** Create a shared validation module with `validate_numeric(value)` that handles the boolean bypass guard. This would have prevented the same bug in 5 stories.

### 2. Unimplemented Features Marked Complete (Story 3-5)

Story 3-5's code review discovered that Task 4.2 (HTMX partial for adaptive tuning section) was marked `[x]` in the story file but was not actually implemented. The review had to create the missing `_adaptive_tuning.html` partial and corresponding route.

**Impact:** If code review hadn't caught this, the settings page would have had a broken lazy-load section.

**Lesson:** Task completion checkmarks should be verified against actual file existence, not just dev self-reporting.

### 3. SSE Event Handling Gaps (Story 3-6)

Story 3-6's code review found that the SSE list re-render in `_generate_sse_events()` was missing the `urgency_scores={}` parameter. This meant urgency badges disappeared when investigations updated via SSE.

**Impact:** Real-time updates broke the urgency column in the investigation list — a visible UI regression that wouldn't appear in unit tests (SSE rendering tested separately from urgency integration).

**Lesson:** When adding new data to list views, check all rendering paths including SSE re-renders. Consider integration tests that verify SSE-rendered HTML includes new columns.

### 4. Investigator Test Count Instability

Investigator test counts fluctuated during the epic:
- Wave 2 pre-flight + Story 3-4 review: **517 passed**, 3 skipped
- Stories 3-1, 3-3, 3-5, 3-6, 3-7 reviews: **505 passed**, 12 pre-existing async failures

The 12 failures are in `test_llm_client.py` (async test infrastructure) and `test_kb_client.py` (qdrant-client API changes). These have persisted since Epic 2 without investigation.

**Impact:** The fluctuation (517 vs 505) suggests environment-dependent test behavior. Inconsistent baseline counts make it harder to detect real regressions.

**Root Cause:** Never investigated. The 12 failures are dismissed as "pre-existing" in every review.

### 5. Duplicate Utility Functions Across Services

Story 3-7's code review noted that `_iso_to_epoch()` in `NoiseReportService` duplicates `NotificationAuditService._iso_to_epoch()` from Epic 2. Similarly, `_render_error_response` was extracted as a helper during 3-7 review to deduplicate error template rendering.

**Impact:** Low — these are small utility functions. But the pattern of duplicating helpers across services suggests a need for a shared utilities module.

## Key Insights

1. **Foundation-first story sequencing accelerates later stories.** Stories 3-1 and 3-2 established the trust level and confidence gate foundation. Story 3-3 then needed zero backend code. Stories 3-5, 3-6, and 3-7 composed existing services. This is the same pattern that worked in Epic 2 (infrastructure-first, channels-second).

2. **Code review severity decreased as the codebase matured.** Epic 1 averaged ~5 issues/story with occasional CRITICAL finds. Epic 2 had 6 issues/story with 1 CRITICAL per story. Epic 3 had ~5 issues/story with zero CRITICAL. The diminishing severity curve suggests accumulated patterns and conventions are preventing the worst bugs.

3. **Boolean bypass is a Python-specific trap that needs a systemic fix.** Finding the same bug in 5 of 7 stories is a clear signal that ad-hoc validation is insufficient. A shared `validate_numeric()` utility would eliminate this entire class of bugs.

4. **HTMX + SSE is a productive but fragile combination.** HTMX lazy-loading and SSE real-time updates work well independently, but their interaction (SSE re-renders must include all lazy-loaded data) creates subtle integration bugs that unit tests don't catch.

5. **Qdrant sentinel keys are a useful but unconventional pattern.** Using `__gate_thresholds__` as a sentinel key in the `service_trust_levels` collection avoids creating new collections, but it's not a standard Qdrant pattern. Future developers need to understand this convention.

6. **The "all Python" epic was the smoothest delivery.** Zero cross-component risk, zero compilation concerns, consistent test execution. When possible, grouping stories by technology reduces delivery friction.
