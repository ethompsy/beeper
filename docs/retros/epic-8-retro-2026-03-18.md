## What Went Well

### 1. Clean Greenfield Architecture with Layered State Management
Each story built cleanly on its predecessor using a consistent state management pattern: `_create_X_state()` / `_get_X_state(app)` for fault state (8-2), lifecycle state (8-3), and scenario state (8-4). This pattern — storing mutable state in `app.config` dicts with factory functions — enabled runtime control without pod restarts and made each layer independently testable. The architecture emerged naturally from story 8-1's design and scaled elegantly.

### 2. Layered Orchestration Without Code Duplication
The demo platform's most impressive architectural quality is how each story delegates to the layer below: scenarios delegate to lifecycle, lifecycle delegates to fault injection, fault injection operates on the base demo server. This meant zero duplication — scenario runner calls lifecycle start, lifecycle internally calls fault inject, and recovery cascades back down. This layering was explicitly called out in story specs ("CALL these internally, do not duplicate fault logic") and was followed consistently.

### 3. Single-Server Multi-Role Pattern
Story 8-1's decision to use a single Flask server image with `SERVICE_ROLE` env var differentiation was elegant. One Docker image, one codebase, four distinct service behaviors (api-gateway, backend, database, worker). This drastically simplified build complexity, test fixtures (parameterized across roles), and K8s deployment. The pattern proved robust enough to support all subsequent stories without modification.

### 4. NFR Compliance Achieved Deterministically
Both hard NFRs were met with margin:
- **NFR7** (lifecycle < 5 minutes): Default timing sums to 53 seconds — 82% under budget
- **NFR18** (10 consecutive runs): 40 test runs across all 4 fault types, all successful. Deterministic TESTING mode with synchronous execution made this verifiable in CI without flakiness.

### 5. Adversarial Code Review Continues to Find Real Bugs
Every code review found actionable issues:
- Story 8-1: Duplicate `/health` route shadowing (HIGH), wrong pod label selector in Makefile
- Story 8-2: Stale `FAULT_INJECTION_ACTIVE` gauge on fault overwrite (HIGH)
- Story 8-3: Stale `LIFECYCLE_STAGE` gauge on re-start without reset (HIGH), missing trust_level validation
- Story 8-4: Unbounded runs list growth (HIGH), missing try/finally on endpoints

The HIGH issues — stale metrics gauges (8-2, 8-3) and unbounded list growth (8-4) — would all cause production problems during extended demo sessions. Code review caught every one.

## What Could Be Improved

### 1. Recurring Stale Prometheus Gauge Pattern
Stories 8-2 and 8-3 both had the same bug: when a new state overwrites a previous one (new fault type injected over existing, lifecycle restarted), the old Prometheus gauge label remained set to 1 while the new one was also set to 1. This "stale gauge" pattern appeared in 2 of 4 stories and was caught both times by code review. The root cause is that labeled Prometheus gauges require explicit clearing of all previous label values before setting new ones — a pattern that should be documented as a project convention.

### 2. Cascading Failure Cross-Service Not Fully Implemented
Story 8-2 specified that `cascading-failure` should propagate errors from backend to api-gateway via dependency health checking. The implementation simulates cascading failure within a single service (returns errors at configurable rate) but doesn't implement cross-service propagation. This was accepted as "design scope" during code review, but the story spec explicitly described inter-service behavior. The gap between spec and implementation should have been flagged during story creation rather than deferred during review.

### 3. Server.py Growing Large
The demo server (`demo/app/server.py`) grew from 310 lines (8-1) to an estimated 1,000+ lines (8-4). Four layers of routes (base server, fault control, lifecycle, scenarios) with state management, metrics, and narration all in one file. While this is acceptable for a demo app, it would benefit from modularization (e.g., separate blueprint files) if the demo app continues to evolve.

### 4. YAML Scenario Files Are Reference-Only
Story 8-4 created YAML files in `demo/scenarios/` but the server uses embedded Python dicts as the source of truth. The YAML files are documentation artifacts, not loaded by the application. This was accepted as a design decision but creates a maintenance risk — if scenarios are updated in the Python code, the YAML files may drift out of sync.
