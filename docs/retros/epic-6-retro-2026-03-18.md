## What Went Well

### 1. Knowledge Compounding Architecture
Stories 6-1 through 6-5 established a self-improving knowledge base. Every investigation either matches existing KB entries (weighted by validation status) or creates new ones automatically. The semantic similarity threshold (0.85) prevents duplicate KB entries while the validation weighting (proven=1.0 > human-confirmed=0.9 > corrected=0.8 > AI-generated=0.6) ensures quality rises over time. The KB now compounds knowledge with every resolved investigation.

### 2. Signal Correlation Consistency
Stories 6-7, 6-8, and 6-9 followed an identical temporal correlation pattern: strong (<5min), moderate (5-30min), weak (>30min). This consistency across deploy, topology, and change event correlation means the investigation timeline presents a unified confidence model. Evidence extraction automatically populates the timeline without per-type wiring.

### 3. Graceful Degradation Pattern
Every new service and investigator step uses try/except with graceful fallback. Failed K8s API calls, unavailable Git providers, or missing topology data never crash the investigation pipeline. This pattern was established in Epic 5 and consistently applied throughout Epic 6.

### 4. Existing Infrastructure Reuse
Story 6-9 (change events) demonstrated mature architecture: the `config_change` evidence type and `config` source type already existed in EvidenceService. The unified timeline template already rendered config_change events. No new evidence types, source types, or timeline templates were needed — just wiring.

### 5. Pipeline Integration Test Discipline
Adding 3 new pipeline steps (6-7, 6-8, 6-9) required updating 8 integration test files each time. Despite the churn, all updates were done systematically and no regressions occurred.

## What Could Be Improved

### 1. Pipeline Step Index Churn
Adding each new pipeline step cascaded across 8 integration test files (step indices, pipeline length assertions). This happened 3 times in Epic 6 (stories 6-7, 6-8, 6-9). Consider centralizing the expected pipeline step count as a constant or using step name-based assertions instead of index-based ones.

### 2. Duplicated Utility Functions
`_classify_confidence()` and `_format_time_gap()` are copy-pasted identically in `deploy_correlation.py` and `change_event_correlation.py`. The story instructions explicitly prohibited modifying existing steps, which forced the duplication. For Epic 7+, consider extracting shared temporal correlation utilities to a common module.

### 3. Code Review Found Missing Task Implementation (Story 6-3)
Story 6-3's code review found a CRITICAL issue: Task 4.3 ("View Service Knowledge" link in filter panel) was marked [x] but not implemented. This was the only CRITICAL finding in the entire epic. Reinforces the value of adversarial code review — the dev agent marked the task complete without actually implementing it.

### 4. Evidence Extraction Test Coverage
Story 6-9's code review found that `_extract_change_event_references()` lacked explicit unit tests (Task 9.1). The deploy correlation extraction (6-7) also lacked these tests. Both were addressed in code review, but dev agents should add extraction tests proactively.

### 5. Deduplication Edge Case (Story 6-9)
Story 6-9's `_merge_and_deduplicate()` had a bug: it checked duplicates against `events` instead of `combined`, missing duplicates from dual label selectors. Caught in code review. Lesson: deduplication logic needs explicit tests for all duplicate sources.
