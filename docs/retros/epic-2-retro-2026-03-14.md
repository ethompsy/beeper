## What Went Well

### 1. Perfect Zero-Regression Streak

All 7 stories completed with zero test regressions — a significant improvement over Epic 1 which had 3 regressions in Story 1-8. The infrastructure-first approach (Stories 2-1 and 2-2 establishing the foundation) meant subsequent stories built on stable ground without breaking existing functionality.

### 2. Excellent Architecture Layering Strategy

The epic naturally decomposed into three layers:
- **Rust infrastructure** (Stories 2-1, 2-2): CRD, outbox, routing engine — operator-level concerns
- **Cross-component bridge** (Story 2-3): Connected Rust outbox worker to Python delivery service
- **Python delivery channels** (Stories 2-4 through 2-7): All channel implementations in Python

After Story 2-3 established the Rust→Python bridge, Stories 2-4 through 2-7 were entirely Python-only, eliminating cross-component risk for 57% of the epic. This reduced complexity and allowed faster iteration.

### 3. Consistent Code Review Rigor

Every story had exactly 6 issues found during adversarial code review, maintaining the discipline established in Epic 1. Every story had at least 1 CRITICAL issue caught exclusively by review:
- **2-1:** Missing `POST /api/v1/notifications/outbox` endpoint (entire write path was absent)
- **2-2:** Severity enum serde inconsistency (PascalCase vs lowercase)
- **2-3:** Task descriptions inaccurately reflected delegation-to-UI architecture
- **2-4:** Dead parameters in `resolve_incident()` (unused `payload`/`base_url`)
- **2-5:** Missing digest flush endpoint route tests (8 tests gap)
- **2-6:** `import json` not at module top (repeat of 2-3 finding)
- **2-7:** Unguarded `response.json()` for JSONDecodeError in test notification flow

### 4. Minimal Dependency Footprint

Only 2 new dependencies across 7 stories:
- `chrono-tz = "0.10"` (Rust, Story 2-2) — required for IANA timezone support in quiet hours
- `slack-sdk ^3.27` (Python, Story 2-3) — Slack's official SDK for Block Kit and rate limiting

PagerDuty used direct httpx (existing dep). Email used smtplib/email.mime (Python stdlib). Webhooks used httpx (existing dep). This continues the "zero new dependencies unless justified" policy from Epic 1.

### 5. Cumulative Previous Story Intelligence

Each story's dev notes grew richer with cross-story pattern recognition. By Story 2-7, the intelligence section referenced recurring patterns discovered across the entire epic: imports at module top, mock paths matching import paths, error context in returns, payload schema documentation, ruff isort compliance. This institutional memory prevented repeated mistakes.

### 6. Comprehensive Test Growth

A strong error handling pattern emerged across all channel integrations: every channel consistently classifies errors as retryable (429, 5xx, timeouts, connection errors) vs non-retryable (4xx auth/config errors). This pattern was established in Story 2-3 (Slack) and consistently applied through 2-4 (PagerDuty), 2-5 (email/webhook), creating a predictable retry model across all delivery channels.

## Challenges & Growth Areas

### 1. Cargo Not Available — Rust Compilation Still Deferred (CRITICAL, carried from Epic 1)

The single largest risk carries forward unchanged: **Rust code was never compiled or tested locally.** Stories 2-1 and 2-2 added ~65 Rust tests that remain unverified by compilation. The Epic 1 retrospective flagged this as CRITICAL with 3 action items to install the Rust toolchain — none were completed.

**Impact:** If CI reveals compilation errors, Rust stories from both Epic 1 (6 stories) and Epic 2 (2 stories) may need simultaneous rework.

**Root Cause:** Development environment still lacks a Rust toolchain installation.

### 2. Investigator Test Count Drop (12 pre-existing async failures)

Between Stories 2-3 and 2-4, investigator test count dropped from 517 to 505 with 12 "pre-existing async failures" noted as unrelated to Epic 2 changes. These failures persisted through Stories 2-4 through 2-7 without being addressed.

**Impact:** 12 tests silently broken. While confirmed unrelated to notification code, they represent degrading test health in the investigator component.

**Root Cause:** Likely a transient environment or dependency issue in the async test infrastructure, but never investigated.

### 3. Recurring Code Review Pattern: Import Placement

The same issue — `import json` not at module top — was found in both Story 2-3 (`notification_service.py`) and Story 2-6 (`notification_audit_service.py`). Despite being caught and fixed in 2-3, the same mistake recurred in 2-6.

**Lesson:** Ruff's isort rules should catch this automatically. The fact that it didn't suggests the import was inside a function body (lazy import), which ruff doesn't flag by default. Consider enabling stricter import linting rules.

### 4. Duplicate Test Fixtures Across Test Files

Multiple stories (2-5, 2-7) had duplicate `_RoleClient` test fixtures in individual test files instead of using `conftest.py` shared fixtures. This was caught in code review each time but suggests a pattern where new test files copy-paste setup code rather than reusing existing infrastructure.

**Lesson:** Establish a clear "test file template" that imports from conftest.py. Document shared test fixtures in a discoverable location.

### 5. Routing Rules UI Limitation

Story 2-7's notification configuration UI shows placeholder text ("Managed via CRD routing rules") for routing configuration because the operator API's channel list endpoint does not return routing config. This is a known UX gap where the UI cannot fully represent the channel's behavior.

**Impact:** Low — users configure routing via CRD YAML, so the UI is informational only. But it reduces the UI's value as a verification tool.

## Key Insights

1. **Infrastructure-first, channels-second is the right sequencing.** Stories 2-1 and 2-2 (CRD + routing) established the foundation. Story 2-3 (Slack) bridged Rust→Python. Stories 2-4-2-7 were pure Python delivery. This created an accelerating velocity curve — later stories were faster because the infrastructure was stable.

2. **Cross-component stories (2-3) are the highest-risk stories.** Story 2-3 was the only story touching both Rust and Python, and it required the most careful integration (outbox worker calling UI delivery endpoint). All subsequent stories avoided cross-component changes by design.

3. **6 issues per code review is a stable equilibrium.** Both Epic 1 (~5/story) and Epic 2 (6/story) show consistent review findings. This isn't a sign of low quality — it's the natural rate at which adversarial review catches edge cases, missing tests, and documentation gaps that self-review misses.

4. **The delegation-to-UI pattern works well.** The Rust outbox worker delegates actual channel delivery to the Python UI service via HTTP. This keeps channel-specific logic (Slack SDK, SMTP, httpx) in Python where it's easier to test and iterate, while the Rust operator handles persistence and retry. Worth maintaining this architecture for any future channels.

5. **HMAC-SHA256 webhook signing is a good security pattern.** Story 2-5 implemented optional webhook signing. This should be the default for any external integration to prevent payload tampering.

6. **Qdrant payload-only collections are a versatile pattern.** Used for notification_outbox (2-1) and notification_audit (2-6), payload-only collections (no vector index) serve as durable, queryable event stores. This pattern works well for operational data that needs filtering but not semantic search.
