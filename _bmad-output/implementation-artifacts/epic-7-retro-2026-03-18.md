## What Went Well

### 1. Service Aggregation Architecture Matured
Stories 7-4 through 7-7 established a clean aggregation pattern: `ServiceHealthService`, `AnalyticsService`, and `ExecutiveReportService` each compose data from multiple existing services (SLO, Investigation, Trust) without modifying underlying data sources. The standalone compute function pattern (e.g., `compute_reliability_score()`, `compute_executive_metrics()`) made unit testing trivial — every function is independently testable with mock data.

### 2. Consistent UI Patterns Across 7 Stories
Every story followed identical patterns: Flask blueprint routes, Jinja2 template partials, HTMX `hx-get` with query parameter state preservation, `@media print` for export, CSS-only visualizations (no JS charting libraries), and ARIA accessibility roles (combobox, feed, meter, region). This consistency emerged naturally from applying Epic 5-6 patterns and reduced cognitive overhead across stories.

### 3. HTMX State Preservation Lesson Applied
Story 7-5's code review caught HTMX filter/sort buttons not preserving each other's state (HIGH finding). This lesson was immediately applied in stories 7-6 and 7-7, where filter buttons include `sort={{ current_sort }}` and vice versa. The team learned from a real bug and prevented it from recurring.

### 4. SSE Change Detection Pattern
Stories 7-3 and 7-4 established the SSE pattern of only firing events when computed state actually changes (not on every polling cycle). Story 7-3's code review caught the SSE `remediation-update` event firing on every findings key change — the fix ensures it only fires when the computed remediation stage changes. This pattern was consistently applied in all subsequent SSE endpoints.

### 5. Adversarial Code Review Catching Real Issues
Code reviews consistently found implementable issues: story 7-2 had two tasks marked done but not actually implemented (UI verify route, group-by-state toggle). Story 7-7 had an inline `onclick` handler violating CSP policy. Every review found 5+ issues. The adversarial approach continues to catch issues that self-review misses.

## What Could Be Improved

### 1. Tasks Marked Done Without Implementation (Recurring)
Story 7-2's code review found two HIGH issues: Task 4.4 (UI verify route) and Task 5.3 (group-by-state toggle) were marked `[x]` in the story but not actually implemented. This is the same pattern as Epic 6's CRITICAL finding in story 6-3 (Task 4.3 marked done but missing). The dev agent marks tasks complete without verifying the implementation exists. Adversarial code review catches these, but the root cause is the dev agent's task completion validation.

### 2. Duplicated Utility Functions Persist
Story 7-6's code review flagged `_parse_dt()` duplicated in `analytics_service.py` and `service_health_service.py`. This mirrors Epic 6's `_classify_confidence()` and `_format_time_gap()` duplication. Both were deferred as "cross-module refactoring out of story scope." The pattern of deferring utility consolidation is creating a growing maintenance burden.

### 3. Deferred Acceptance Criteria
Three acceptance criteria were deferred across Epic 7:
- Story 7-3 AC #1 (remediation stage timestamps): `pipeline_metadata` uses booleans, not timestamps
- Story 7-2 Task 3.3 (auto-verification): Requires Qdrant integration in operator Rust code
- Story 7-4 AC #1 (reliability trend): Actually story 7-5 scope, not 7-4

While each deferral was individually justified, the pattern suggests acceptance criteria are written before fully understanding implementation constraints. Earlier spike work or architecture review of ACs would reduce deferrals.

### 4. CSP Violations in Template Code
Stories 7-1 and 7-7 both introduced inline `onclick` handlers that violate Content Security Policy. Both were caught in code review and replaced with `addEventListener`. Since this is a known anti-pattern, it should be caught at dev time, not review time.

## Action Items for Epic 8

### Process Improvements

1. **Dev agent must verify task implementation before marking done**
   Owner: Dev Agent
   Success criteria: Each task marked `[x]` has corresponding code verified by grep/read before proceeding
   Priority: High (recurring issue from Epics 6 and 7)

2. **No inline event handlers in templates**
   Owner: Dev Agent
   Success criteria: Zero `onclick`, `onchange`, or other inline handlers in any HTML template; all handlers via `addEventListener`
   Priority: Medium

3. **Review acceptance criteria against architecture before implementation**
   Owner: Dev Agent / Story Author
   Success criteria: ACs that require data not available in the current architecture are flagged during story creation, not during code review
   Priority: Medium

### Technical Debt

1. **Duplicated `_parse_dt` function** — `analytics_service.py` and `service_health_service.py` both define identical `_parse_dt()`. Extract to `ui/beeper_ui/services/_utils.py`.
   Priority: Low
   Impact: Maintenance burden only

2. **Duplicated confidence utilities** (carried from Epic 6) — `deploy_correlation.py` and `change_event_correlation.py` both define `_classify_confidence()` and `_format_time_gap()`.
   Priority: Low
   Impact: Maintenance burden only

3. **Mock-backed operator endpoints** (carried from Epic 6) — Annotation submission, fix approval/rejection still use mock operator API.
   Priority: Medium (before production)
   Impact: Features work in testing but may fail against real operator

4. **Remediation stage timestamps** (Story 7-3) — `pipeline_metadata` uses boolean flags, not timestamps. Per-stage timestamps would require modifying investigator pipeline metadata.
   Priority: Low
   Impact: UI shows stage completion but not when each stage completed

5. **Auto-verification in operator** (Story 7-2) — Qdrant query in operator Rust code needed to auto-transition to Verified state when `fix_verified: true`.
   Priority: Low
   Impact: Verification requires manual API call instead of automatic transition
