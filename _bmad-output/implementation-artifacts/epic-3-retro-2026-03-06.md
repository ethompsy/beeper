## What Went Well

### 1. Step Pipeline Architecture Enabled Rapid Extension

Story 3-3 established the `InvestigationStep` protocol and pipeline framework. Each subsequent story (3-4 through 3-8) added a new step by implementing the same interface — constructor dependency injection, `execute() -> StepResult`, consistent data schema. This pattern meant stories 3-4 through 3-8 each followed a proven template, reducing implementation risk and enabling predictable delivery.

### 2. Adversarial Code Reviews Caught Real Issues Every Time

Every story underwent adversarial code review, and every review found meaningful issues. HIGH severity findings included:
- NaN input poisoning EWMA detectors permanently (3-1)
- Investigation name collisions on same-second anomalies (3-1)
- Silent data loss on Qdrant persist failure (3-2)
- `screening_model` fallback bypassing Azure/Ollama provider prefix (3-3)

These weren't cosmetic — they were bugs that would have caused production failures. The consistent code review practice prevented them from shipping.

### 3. Graceful Degradation as First-Class Pattern

Starting with Story 3-3, every step was designed to never fail fatally. KB unavailable? Continue without prior research. LLM call fails? Fall back to raw data summaries. Embedding model not configured? Skip semantic search with a warning. This approach was documented in dev notes and enforced in reviews, producing a resilient investigation pipeline that degrades gracefully under partial system failures.

### 4. Two-Phase LLM Approach Proved Effective

Story 3-5 (Signal Correlation) pioneered the two-phase LLM pattern: Phase 1 generates queries, Phase 2 analyzes results. This was reused in subsequent stories and provided a clean separation between data gathering and synthesis. The pattern kept LLM prompts focused and reduced hallucination risk.

### 5. Pre-Existing Test Failures Were Tracked and Isolated

Throughout the epic, 6 pre-existing async test failures in `test_llm_client.py` (missing `pytest-asyncio`) and 2 in `test_kb_client.py` (qdrant-client API changes) were consistently noted but never confused with new regressions. This discipline ensured accurate quality assessment per story.

## What Could Be Improved

### 1. Pipeline Metadata Passing Required Mid-Epic Refactor

Story 3-6 (RCA Hypothesis) needed access to prior step results but the step pipeline only merged results after all steps ran. The `_pipeline_metadata` dict was introduced as a solution, but it required modifying the agent's `_run_steps()` loop — affecting all prior steps' test mocks. This coupling could have been designed upfront in Story 3-3 when the step framework was created.

**Action:** When creating extensible frameworks, anticipate inter-step data flow in the initial design.

### 2. String "null" From LLM Responses Was a Recurring Bug Pattern

LLMs frequently returned the string `"null"` instead of JSON `null` for optional fields. This was caught and fixed in stories 3-6, 3-7, and 3-8 independently. A shared normalization utility would have prevented repeated fixes.

**Action:** Add a shared `_normalize_llm_value()` helper to the `steps/__init__.py` module for common LLM response cleaning.

### 3. Model Tier Keys Collided in Pipeline Metadata

Story 3-9 discovered that all steps wrote `model_tier` and `model_used` to the same pipeline metadata dict, causing later steps to overwrite earlier steps' values. The fix was to namespace keys per step (e.g., `impact_model_tier`, `rca_model_tier`). This collision was predictable from the metadata merge design.

**Action:** Establish key namespacing conventions in the step protocol documentation for pipeline metadata.

### 4. Pre-Existing Test Failures Persisted Across the Entire Epic

The 6 async test failures in `test_llm_client.py` and 2 in `test_kb_client.py` were noted in every story but only partially addressed mid-epic (Story 3-6 fixed some). These pre-existing failures made it harder to confirm zero regressions with confidence.

**Action:** Fix pre-existing test failures at the start of an epic, not during story execution.

## Lessons Learned for Epic 4

### Technical Patterns to Follow

- Use the `InvestigationStep` protocol for any pipeline extension — proven extensible across 6 steps
- Design inter-step data flow upfront when creating pipeline frameworks
- Namespace metadata keys per step to prevent pipeline collision
- Handle LLM string `"null"` responses with shared normalization utilities
- Two-phase LLM calls (generate → analyze) for complex multi-source tasks
- Graceful degradation as default — every operation returns a valid result even on failure
- SHA-256 cache key generation for deterministic LLM response caching
- `select_model(tier)` for tiered model routing — screening/standard/deep_rca

### Testing Patterns

- Use `_make_step()` helper pattern for step unit tests — proven across 6 test files
- Use `_full_pipeline_metadata()` fixture for steps that consume prior results
- Mock `LlmClient.complete_sync()` and `embed_sync()` — never make real LLM calls in tests
- Mock `KBClient` methods — never connect to real Qdrant in unit tests
- Test all graceful degradation paths explicitly (every failure mode gets a test)
- Consistent `StepResult.data` schema across all code paths (learned from MEDIUM-3 in 3-4)
- Fix pre-existing test failures at epic start, not during story execution

### Process Patterns

- Adversarial code review on every story — caught 52 issues across the epic
- Step-by-step pattern reuse accelerated delivery (stories 3-4 through 3-8 followed established patterns)
- Dev Notes referencing prior story learnings created institutional knowledge chain
- Pipeline metadata schema must be documented and validated in step protocol
- Code review records in story files create traceable quality history
