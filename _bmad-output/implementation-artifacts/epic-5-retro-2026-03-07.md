## What Went Well

### 1. Layered Architecture Enabled Progressive Feature Stacking

Each story built cleanly on the previous one's data model and service layer:
- 5-1 established the `corrections` collection, `Correction`/`CorrectionMessage` dataclasses, and `CorrectionService` with LLM integration
- 5-2 extended `CorrectionService` with `generate_revision()`/`refine_revision()`, reusing the existing correction conversation data
- 5-3 hooked into 5-2's apply route (non-blocking), added `LearningPattern` storage and `LearningService`
- 5-4 consumed 5-3's learning patterns for accuracy calculation and built the trust graduation system on top

No story required reworking a previous story's code. The architecture was designed for progressive layering from the start.

### 2. Non-Blocking Hook Pattern Prevented Cascade Failures

Stories 5-3 and 5-4 both hooked into the `kb_apply_revision()` route using try/except wrappers. Learning analysis and trust re-evaluation both run after the core revision is applied, but failures in either hook don't block the revision. This pattern was established in 5-3 and cleanly extended in 5-4, preventing auxiliary features from degrading the primary correction workflow.

### 3. LLM Integration Via litellm Proved Lightweight and Effective

Rather than importing from `beeper_investigator` (which isn't available in the UI virtualenv), both `CorrectionService` and `LearningService` used `litellm` directly. This kept the UI package self-contained while providing full LLM capability for:
- Correction acknowledgment (5-1)
- Revision generation and refinement (5-2)
- Diff analysis and pattern categorization (5-3)
- Prompt adjustment generation (5-3)

The `_complete_sync()` pattern with JSON response parsing and fallback was reused across all LLM calls.

### 4. Adversarial Code Reviews Maintained High Quality Bar

All 4 stories underwent adversarial code review, producing 23 total issues (6 HIGH, 13 MEDIUM, 4 LOW). Every HIGH and MEDIUM issue was fixed. Key catches:
- Duplicate Qdrant queries in service methods (5-4 HIGH: `upsert_service_trust` queried twice)
- Error message leaking internal details (5-2 MEDIUM, 5-3 MEDIUM, 5-4 HIGH)
- Missing input validation (5-4 HIGH: `service_name` path param unvalidated)
- Double LLM call in prompt context API (5-3 HIGH: called `generate_prompt_adjustments` twice)
- Entry ID mismatch not validated in apply route (5-2 HIGH)

### 5. Consistent Data Model Pattern Across Qdrant Collections

Epic 5 added 3 new Qdrant collections (`corrections`, `learning_patterns`, `service_trust_levels`) all following the same payload-only pattern with dummy vectors `[0.0]`. Each had a corresponding dataclass with `from_qdrant()` classmethod. This consistency made each new collection trivial to implement and test.

## What Could Be Improved

### 1. Error Message Sanitization Was a Recurring Review Finding

Stories 5-2, 5-3, and 5-4 all had routes that passed `str(e)` directly to templates or JSON responses, leaking Qdrant internal error details to users. This was caught and fixed in every code review.

**Action:** Establish a pattern of generic user-facing error messages with `logger.warning()` for details. Consider a shared error response helper.

### 2. Missing Input Validation Caught Late

Story 5-4's `service_name` path parameter had no validation (could accept any string, including injection attempts). This was only caught in the adversarial code review.

**Action:** Validate all user-supplied path parameters at route entry. Use regex patterns for constrained values (alphanumeric + hyphens, max length).

### 3. Duplicate Qdrant Queries in Service Methods

Story 5-4's `upsert_service_trust` called `get_service_trust()` (one scroll) then did a separate scroll to find the point ID. This doubled the Qdrant load for every upsert.

**Action:** When a method needs to check existence AND get the point ID, do a single scroll query rather than calling a get method followed by another query.

### 4. Swallowed Exceptions Hid Potential Issues

Story 5-4 had `except Exception: pass` in the upsert method, silently dropping errors that could cause duplicate trust records. Code review added `logger.warning()`.

**Action:** Never use bare `except: pass`. Always log swallowed exceptions, even in non-critical paths.

### 5. Boundary Test Coverage Required Review Nudge

Story 5-4's graduation logic had exact threshold boundaries (>=10 entries, >=90% accuracy, <80% downgrade) but no tests at those exact boundaries. Tests only covered clear pass/fail cases. Code review added 4 boundary tests.

**Action:** When implementing threshold-based logic, always include boundary tests at the exact threshold values.

### Prompt Templates

Each LLM method uses a dedicated `*_SYSTEM_PROMPT_TEMPLATE` constant with clear instructions, response format specification, and temperature 0.0 for consistency.

### Error Handling

- LLM failures return graceful fallbacks (generic acknowledgment for corrections, empty list for patterns)
- Non-blocking hooks: LLM analysis in apply route wrapped in try/except
- Generic error messages to users; detailed errors logged via `logger.warning()`

## Human-AI Collaboration System

Epic 5 built a complete human-AI collaboration loop:

```
1. Beeper creates KB entry (investigation documentation)
        ↓
2. SRE reviews → provides conversational correction (5-1)
        ↓
3. Beeper generates revision from correction (5-2)
        ↓
4. SRE reviews diff → approves or refines (5-2)
        ↓
5. On apply: Beeper learns from diff patterns (5-3)
        ↓
6. Learning patterns feed accuracy metrics (5-3)
        ↓
7. Accuracy metrics drive trust graduation (5-4)
        ↓
8. Trusted services → Beeper auto-publishes future entries (5-4)
        ↓
9. Auto-published entries still reviewable → loop continues
```

This creates a virtuous cycle where human corrections make Beeper more accurate, which builds trust, which reduces the review burden, while maintaining transparency and override capability.
