## What Went Well

### 1. Progressive Pattern Reuse Across All 7 Stories

Each story explicitly built on patterns established by its predecessors. Story 2-1 established KBService, HTMX partials, and markdown rendering. Story 2-2 added EmbeddingService and vector search. By Story 2-7, the development team was efficiently composing features from a rich library of proven patterns:
- CSS-only tab switching (`:has()` pseudo-class) — introduced in 2-4, reused in 2-5 and 2-7
- `validate_import_data()` + `parse_tags()` — created in 2-4, reused in 2-5
- HTMX partial response pattern — standardized in 2-1, used consistently through 2-7
- KBService layered extensions — each story added methods without modifying existing ones

### 2. Adversarial Code Reviews Caught Real Production Issues

Every story underwent adversarial code review, catching security and correctness issues:
- **Story 2-1:** Removed `img` tag from bleach whitelist to prevent data URL attacks (MEDIUM)
- **Story 2-2:** Missing query sanitization could expose search to injection (HIGH)
- **Story 2-4:** YAML front matter parsing crash on missing closing `---` (HIGH)
- **Story 2-5:** Missing optimistic concurrency control for concurrent edits (AC4)
- **Story 2-7:** "Compare with current" links always 404'd — current version wasn't in snapshots (CRITICAL)

The CRITICAL finding in Story 2-7 (diff links broken for current version) would have been immediately visible to users. The `_entry_as_version()` fallback pattern that fixed it demonstrates how reviews catch integration gaps that unit tests miss.

### 3. CSS-Only Interactivity — Zero JavaScript

The entire KB UI was built without a single line of JavaScript. All interactive behaviors used:
- HTMX for server-driven dynamic updates (`hx-get`, `hx-post`, `hx-trigger`, `hx-target`)
- CSS `:has()` pseudo-class for tab switching and toggle visibility
- CSS-only accordions for filter panels

This matched the architecture mandate ("No JavaScript complexity") and resulted in a fast, accessible UI.

### 4. Security-First Markdown Rendering

Story 2-1 established a comprehensive XSS prevention pattern using `bleach` for HTML sanitization, which was consistently applied throughout the epic. The `strip_markdown` and `highlight_query_terms` utilities provided safe text processing for search results. No security regressions were introduced across 7 stories.

### 5. Qdrant Collection Design for Version History

Story 2-6's decision to create a separate `knowledge_versions` collection (rather than storing versions in the main `knowledge` collection) was architecturally sound:
- Kept semantic search results clean (only current versions returned)
- Eliminated need for embedding vectors on historical snapshots
- Simplified queries for both current entries and version history

## What Could Be Improved

### 1. Route Ordering Was a Recurring Issue

Stories 2-2 and 2-4 both encountered route ordering conflicts with Flask's dynamic `/<entry_id>` route. Static routes like `/search` and `/import` had to be registered BEFORE the dynamic route to prevent them from being swallowed. This was caught in code review (2-2 MEDIUM) and proactively handled in 2-4, but it remained a gotcha throughout the epic.

**Action:** Document Flask route ordering rules in architecture patterns: static routes always before dynamic `/<path>` routes in blueprint registration.

### 2. Embedding Service Configuration Check Was Missed Repeatedly

Stories 2-4, 2-5, and 2-6 all had code review findings about missing `embedding_service.is_configured()` checks before write operations. Despite being documented in dev notes, each story repeated the omission.

**Action:** Add `is_configured()` check to KBService write methods themselves (create_entry, update_entry) rather than relying on route-level checks.

### 3. Test Count Reporting Was Inconsistent

Story files reported test counts differently — some reported total UI tests, some reported only KB-specific tests, some reported cumulative totals. This made it difficult to track actual test growth across the epic.

**Action:** Standardize test reporting: always report (a) new tests added and (b) total test suite count.

### 4. Severity Filter Not in Qdrant Schema

Story 2-3 discovered that `severity` was listed in AC2's filter requirements but was never added to the Qdrant schema (init-collections.py). The AC was amended with a documented deviation. This was a planning gap — the filter was specified without verifying schema support.

**Action:** Cross-reference filter/search requirements with actual Qdrant schema during story creation, not during implementation.

## Patterns Established in Epic 2

### Technical Patterns
- **KBService pattern:** Lazy Qdrant client initialization, scroll/filter for browsing, vector search for semantic queries
- **EmbeddingService singleton:** LRU-cached embedding generation, `is_configured()` guard, `reset_embedding_service()` for tests
- **CSS-only interactivity:** `:has()` pseudo-class for tab/toggle switching, no JavaScript
- **HTMX partial loading:** `hx-get`, `hx-post`, `hx-trigger`, `hx-target`, `hx-indicator` for all dynamic UI
- **Markdown XSS prevention:** `bleach` sanitization with strict tag whitelist, `strip_markdown` for plain text contexts
- **Version snapshot collection:** Separate `knowledge_versions` collection with zero vectors for non-searchable history
- **Diff generation:** `difflib.unified_diff()` with structured hunk parsing, plain text rendering (no HTML in diffs)
- **Import validation:** `validate_import_data()` + `parse_tags()` reusable validation, `ImportResult` dataclass

### Testing Patterns
- Mock Qdrant client at the service boundary, not at route level
- Use `_make_entry()` helpers for test data factories
- Test all HTMX partial responses for correct template rendering
- Test XSS prevention with malicious input samples
- Test embedding service not-configured paths explicitly
- Test validation edge cases (empty, too long, invalid characters)

### Process Patterns
- Adversarial code review on every story — caught 46 issues across the epic
- Route ordering discipline: static routes before dynamic `/<entry_id>` routes
- CSS-only UI interactions as default (no JavaScript unless absolutely necessary)
- Embedding service configuration check before all write operations
- Filter cache invalidation after write operations
