# Story 2.4: Fix LLM Root Cause Analysis & Recommendations

Status: done

## Story

As a **demo operator (Eric)**,
I want investigations to produce specific, evidence-backed root cause hypotheses and actionable recommendations,
So that Diana sees real AI reasoning about infrastructure problems — not generic guesses.

## Background

Story 2.2 fixed signal gathering (Prometheus & Loki data flows into the investigator). Story 2.3 fixed KB integration (prior incidents are searchable). Now the LLM must use that real data to produce useful output. Two steps are in scope: `RCAHypothesisStep` (step 7 of 16) and `ResolutionRecommendationStep` (step 8 of 16). Both use LiteLLM to call Anthropic Claude.

**Epic 2 dependency chain:** 2.1 (lifecycle) → 2.2 (signal gathering) → 2.3 (KB integration) → **2.4 (LLM RCA)** → 2.5 (ServiceLevel CRD)

**PRD success criterion:** "payment-failure fault injection produces a specific, evidence-backed investigation 3/3 consecutive runs." The PRD user journey expects inline Prometheus metric values and Loki log excerpts (e.g., "HTTP 5xx error rate spiked to 34% on paymentservice").

## Acceptance Criteria

1. **Given** the investigator has gathered Prometheus metrics, Loki logs, and KB results
   **When** it sends context to the LLM for root cause analysis
   **Then** the LLM prompt includes actual signal data (metric values, log excerpts) — not just service names **(FR18)**
   **And** the response contains a specific root cause hypothesis referencing the observed evidence

2. **Given** the LLM generates a root cause hypothesis
   **When** the investigator requests resolution recommendations
   **Then** the response includes specific, actionable recommendations (e.g., "Scale payment service replicas from 2 to 4") rather than generic advice (e.g., "Check the service") **(FR19)**

3. **Given** the LiteLLM provider is configured for Anthropic Claude
   **When** the investigator makes LLM calls
   **Then** calls complete successfully within 10 minutes total investigation time at p95 **(NFR3, NFR15)**

4. **Given** the full investigation pipeline has executed
   **When** all steps complete
   **Then** non-LLM steps complete within 2 minutes of CRD creation **(NFR2)**

## Dev Notes

### Architecture Context

- **Pipeline position:** RCAHypothesisStep is step 7 of 16, ResolutionRecommendationStep is step 8. Both receive `pipeline_metadata` dict containing all prior step results via `agent.py:349`
- **LLM tiers:** RCA uses `deep_rca` tier (can configure separate model via `BEEPER_LLM_DEEP_RCA_MODEL`), recommendations use `standard` tier
- **Model defaults:** Production `claude-sonnet-4`, dev `claude-3-5-haiku-20241022`
- **Token budget:** Both steps request `max_tokens=1024` for response; input prompt uncapped (Claude supports 100K+ context)
- **Temperature:** Both steps use `temperature=0.0` (deterministic, cache-friendly)
- **PII scrubbing:** Applied automatically before LLM calls (`scrubber.py:88-180` — scrubs credentials, IPs, JWT tokens, API keys)

### Known Data Flow Gaps

1. **Signal data summarization:** `signal_correlation._format_signals()` (line 575) reduces raw Prometheus/Loki responses to count + summary text. Actual metric values (percentiles, rates, thresholds) and log excerpts are lost before reaching RCA
2. **Temporal summary unused:** Signal correlation returns `temporal_summary` in its output but RCA prompt doesn't include it
3. **Fallback recommendations are generic:** When LLM fails, fallback actions say "Review service health dashboards" regardless of gathered signals
4. **KB resolution promotion may exceed cap:** Prepending KB resolution without dedup check can produce 6+ recommendations (cap is 5)
