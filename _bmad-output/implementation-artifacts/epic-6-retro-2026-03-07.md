## What Went Well

### 1. Service Extension Pattern Enabled Zero-Friction Feature Stacking

Each story built on the previous story's infrastructure without requiring rework:
- 6-1 established `MetricsService` with the Qdrant scroll+cache pattern, SVG chart computation, category bars, HTMX filtering, and JSON/CSV export
- 6-2 created `SpendingService` reusing the exact same scroll+cache pattern from 6-1, plus `CostTracker` in the investigator LLM client
- 6-3 extended `SpendingService` with 7 new methods rather than creating a new service class, reusing the cached scroll data for all cost breakdown aggregations

No Qdrant schema changes, no new collections, no duplicate infrastructure. All three stories read from the existing `investigations` collection.

### 2. Server-Rendered SVG Charts Eliminated JavaScript Dependencies

All three stories used inline SVG for data visualization (trend lines, category bars, progress bars) computed server-side. This kept the frontend stack simple:
- No charting library dependencies
- No JavaScript bundle to maintain
- Charts render on first page load (no flash of unstyled content)
- Consistent rendering across browsers
- HTMX partial swaps work seamlessly with SVG content

The `_compute_spend_chart_data()` helper established a reusable pattern for coordinate computation.

### 3. HTMX Filtering Pattern Provided Consistent UX Across All Dashboards

All three dashboards (MTTR, Spending, Cost Insights) use the identical HTMX pattern:
- Period selector with `hx-get` targeting a content div
- HTMX partial route returning `_content.html` template
- Full page route detecting `HX-Request` header for initial vs HTMX loads
- Export buttons linking to download routes

This consistency means users learn the interaction pattern once and it works everywhere.

### 4. Adversarial Code Reviews Caught Critical Integration Issues

Each story's code review found exactly 7 issues. The most impactful catches:
- **6-2 CRITICAL:** `update_spend()` was never called in the agent — spending caps were defined but never enforced. Review added cost feedback in `agent.run()`
- **6-1 CRITICAL:** N+1 query pattern — each MTTR calculation re-scrolled Qdrant. Review added scroll caching
- **6-3 HIGH:** `get_high_cost_services()` ignored the user-selected period filter, always using "month" regardless of UI selection
- **6-3 HIGH:** Task 1.4 marked complete but `get_cost_trend_by_service()` method never implemented

The 6-2 critical finding (caps never enforced) would have made the entire spending caps feature non-functional in production.

### 5. Environment Variable Configuration Pattern Proved Clean and Flexible

All configurable thresholds use environment variables with sensible defaults:
- `BEEPER_LLM_DAILY_CAP_CENTS` / `BEEPER_LLM_MONTHLY_CAP_CENTS` (disabled when unset)
- `BEEPER_INVESTIGATION_RATE_LIMIT` (disabled when unset)
- `BEEPER_COST_HIGH_THRESHOLD_MULTIPLIER` (default 2.0)

Features are disabled-by-default when env vars aren't set, preventing misconfiguration. Validation with try/except guards against malformed values.

## What Could Be Improved

### 1. Spending Caps Integration Required Cross-Package Changes

Story 6-2 required changes to both the `investigator` and `ui` packages — `CostTracker` lives in the investigator LLM client, while `SpendingService` lives in the UI. The code review caught that the integration between them (calling `update_spend()` with cost feedback) was completely missing.

**Action:** When a story spans multiple packages (investigator + UI), explicitly include integration verification as a task with a test that validates the data flow end-to-end.

### 2. Task Description Accuracy in Story Files

Story 6-3 task 1.4 was marked `[x]` claiming `get_cost_trend_by_service()` was implemented, but the method was never created. The dev used the existing `get_spending_trend()` instead (which was reasonable), but the task description was misleading.

**Action:** When deviating from the task description during implementation, update the task text to reflect what was actually done rather than marking the original description as complete.

### 3. Dead Code Introduced During Implementation

Story 6-3 imported `re` and defined `SERVICE_NAME_PATTERN` in the routes file but never used either. This was presumably planned for input validation that was then handled differently.

**Action:** Before marking a story complete, search for unused imports and constants. Run `ruff check --select F401` (unused imports) as part of the pre-review checklist.

### 4. Period Filter Consistency Not Caught Until Review

Story 6-3's `get_high_cost_services()` and cost trend chart both ignored the user-selected period filter. The high-cost detection always used "month" and the trend chart showed all-time data. This inconsistency was only caught in the adversarial review.

**Action:** When implementing period-filtered views, ensure ALL data on the page respects the same period selection. Add a test that verifies the period parameter is passed through to all service method calls.

### 5. CSV Export Incomplete Per Acceptance Criteria

Story 6-3 AC 5 explicitly requires "data includes model usage breakdown" but the CSV export only included service rows, omitting model data. The JSON export had it but CSV didn't.

**Action:** When an AC specifies export content requirements, write a test that asserts the specific required fields are present in the export output.

### Common Dashboard Pattern

```python
# Route pattern (all 3 dashboards follow this)
@bp.route("/path")
def dashboard():
    svc = get_service()
    try:
        data = _load_template_data(svc)
        if request.headers.get("HX-Request"):
            return render_template("_partial.html", **data)
        return render_template("full.html", **data)
    except Exception as e:
        logger.exception("Failed: %s", e)
        return render_template("_partial.html", error_message="...")
    finally:
        svc.close()
```

## Cost Management Lessons

### 1. Cost Tracking Must Be Integrated at the Call Site

The CostTracker in the LLM client captures cost at the token level using LiteLLM's `usage` response. This is the only reliable place to track cost — post-hoc estimation from model names is inaccurate.

### 2. Cap Enforcement Requires Closed-Loop Feedback

Story 6-2's critical review finding demonstrated that defining caps without enforcing them provides false security. The spending cap enforcer must receive actual cost feedback from completed LLM calls to make enforcement decisions.

### 3. "High Cost" Detection Needs Relative Comparison

Absolute cost thresholds don't work because cost varies with model tier, investigation complexity, and time period. The multiplier-based approach (flag services > Nx average) adapts to the actual spending distribution.

### 4. Actionable Recommendations Drive Value Beyond Alerting

Simply flagging high-cost services provides awareness. Adding specific recommendations ("tune anomaly detection thresholds", "exclude noisy log patterns") with links to relevant admin pages transforms awareness into action.
